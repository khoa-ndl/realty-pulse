# Scaffold Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up a working, tested, documented Next.js repo for RealtyPulse — no product features yet — with the tooling every later phase (MCP layer, content pipeline, dashboard, signup) builds on.

**Architecture:** A single Next.js (App Router, TypeScript) app at the repo root, pnpm-managed, with Vitest for tests and a `pnpm check` script that runs lint + typecheck + test + build as one pass/fail gate. An env-schema module (`lib/env.ts`) is the one place that knows which environment variables the product needs, validated with Zod so a missing key fails fast with a readable error instead of a cryptic downstream crash.

**Tech Stack:** Next.js (App Router, TypeScript, Tailwind CSS), pnpm, Vitest + React Testing Library, ESLint (Next.js default config), Zod.

**Spec:** [docs/superpowers/specs/2026-10-12-realty-pulse-newsletter-design.md](../specs/2026-10-12-realty-pulse-newsletter-design.md)

## Global Constraints

- Framework: Next.js (React UI + API routes) — per spec Architecture section.
- Package manager: pnpm (installed on this machine; not specified by the spec, builder's call).
- Node version: pinned via `.nvmrc` to the version installed on this machine at scaffold time (confirm with `node -v` before writing the file — do not hardcode a guessed version).
- Supabase, Vercel, the MCP outbound layer, and all AI service integrations are explicitly **out of scope** for this plan — they depend on a provisioned Supabase project and are built starting with the next phase.
- License: MIT (Khoa's call for this portfolio project) — per CLAUDE.md default for personal/open projects.
- `.env` must never be created or edited by the implementer; only `.env.example` (names, no values) is committed.

## Review Focus

- A required environment variable (e.g. `ANTHROPIC_API_KEY`) is missing at runtime — the app should fail immediately with a readable error naming the missing key, not crash deep in an API call. Covered by Task 2's tests.
- `.env` gets committed by accident, leaking secrets before any real secret even exists — covered by Task 1's `.gitignore` step and its verification.
- `.env.example` drifts out of sync with the real set of required variables as the project grows in later phases — covered by Task 3's cross-check test, which fails if the two lists ever diverge.
- `.nvmrc` and `package.json`'s `engines.node` silently disagree after a future Node upgrade, so one machine installs cleanly and another doesn't — covered by Task 1's consistency test.
- `pnpm check` silently passes even when something is actually broken (misconfigured script swallows a failure) — covered by Task 1's deliberate-break verification step.

### Task 2: Environment variable schema validation

**Files:**
- Create: `lib/env.ts`
- Test: `lib/env.test.ts`

**Interfaces:**
- Consumes: nothing from Task 1 beyond the Vitest setup.
- Produces: `getEnv(): Env` in `lib/env.ts` — parses `process.env` against a Zod schema and either returns a typed object or throws `Error` with a message naming every missing/invalid key. `Env` is the exported TypeScript type later phases import instead of reading `process.env` directly.
- Produces: `ENV_KEYS: readonly string[]` — exported array of every key the schema requires, in schema-declaration order. Task 3 imports this to cross-check `.env.example`.

Required keys (from spec's Architecture and Outbound Integration sections — later phases will consume these, this task only declares and validates them): `ANTHROPIC_API_KEY`, `PERPLEXITY_API_KEY`, `KIE_AI_API_KEY`, `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`.

- [ ] **Step 1: Write the failing test for a valid environment**

```ts
// lib/env.test.ts
import { describe, it, expect, beforeEach, afterEach } from "vitest";
import { getEnv, ENV_KEYS } from "./env";

const REQUIRED: Record<string, string> = {
  ANTHROPIC_API_KEY: "test",
  PERPLEXITY_API_KEY: "test",
  KIE_AI_API_KEY: "test",
  NEXT_PUBLIC_SUPABASE_URL: "https://example.supabase.co",
  SUPABASE_SERVICE_ROLE_KEY: "test",
  GMAIL_CLIENT_ID: "test",
  GMAIL_CLIENT_SECRET: "test",
  GMAIL_REFRESH_TOKEN: "test",
};

describe("getEnv", () => {
  const originalEnv = { ...process.env };
  beforeEach(() => {
    for (const k of Object.keys(REQUIRED)) delete process.env[k];
  });
  afterEach(() => {
    process.env = { ...originalEnv };
  });

  it("returns a typed object when every required key is present", () => {
    Object.assign(process.env, REQUIRED);
    const env = getEnv();
    expect(env.ANTHROPIC_API_KEY).toBe("test");
  });

  it("throws naming the missing key when one is absent", () => {
    Object.assign(process.env, REQUIRED);
    delete process.env.PERPLEXITY_API_KEY;
    expect(() => getEnv()).toThrowError(/PERPLEXITY_API_KEY/);
  });

  it("ENV_KEYS lists exactly the required keys", () => {
    expect(new Set(ENV_KEYS)).toEqual(new Set(Object.keys(REQUIRED)));
  });
});
```

- [ ] **Step 2: Run test to verify it fails**

Run: `pnpm test lib/env.test.ts`
Expected: FAIL with "Cannot find module './env'"

- [ ] **Step 3: Implement `lib/env.ts`**

Define a Zod object schema with the eight keys above, each `z.string().min(1)`. Export `ENV_KEYS` as `Object.keys(schema.shape)`. Export `getEnv()` that calls `schema.safeParse(process.env)`; on failure, throw `Error` whose message lists every failing key's path joined with `, ` (use the Zod error's `issues`); on success, return `result.data` typed as `Env` (`export type Env = z.infer<typeof schema>`).

- [ ] **Step 4: Run test to verify it passes**

Run: `pnpm test lib/env.test.ts`
Expected: PASS

- [ ] **Step 5: Commit**

```bash
git add lib/env.ts lib/env.test.ts
git commit -m "feat: add validated env schema module"
```
